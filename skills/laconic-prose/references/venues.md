# Venues

Read this when drafting. Each venue has a reader with a different next step. For PR and issue replies, review comments, release notes and changelogs, read [github-prose.md](github-prose.md) instead.

Before drafting for a repository or a recurring venue, read 2 or 3 recent examples (merged PR bodies, earlier release notes, the writer's last email to that recipient, when supplied) and match their length, format and register. Repository templates and the user's required sections win over this guide.

## Client email

- First sentence: what happened or what the client must do, with the date and amount.
- One topic per paragraph, in the order the client acts on them. An action with a deadline goes in its own short paragraph.
- Courtesy in one line at most. No empathy boilerplate, no 'Rest assured', no offer of more help.
- Name the document or item the client must supply, and what happens if they do or do not.
- End on the action and deadline, then the sign-off. No headings, bold or bullets unless the client must tick off 3 or more items.
- Explain a cause in the client's terms: what their report counts and what the ledger counts, then the timing or rule that separates them. No jargon the client did not use.

## Report or file note

- Finding first, then the evidence, then what remains open.
- Each finding names its source document, period and amount.
- State a limit once, where it applies, in plain words ('The July pays are not checked yet').
- Use headings only when the note runs past a screen. No closing summary that repeats the findings.

## README

- First sentence: what the tool does and for whom, in literal words.
- Install and the first working command come before any feature list.
- Feature bullets start with a verb and name a concrete capability. Cut verbless praise bullets.
- State the licence in one plain sentence. No closing pitch.

## Chat answer

- The answer is the first sentence. Length follows the question.
- Prose unless the content is steps or parallel items. No headings or bold labels on a short answer.
- Give the cause the facts support and the fix, in the order the user acts.
- No restated question, no closing summary, no offer of more help.

## End-of-task report to the user

- First sentence: what is done, in their terms.
- Then the evidence (command and result), checks not run, and anything needing their decision.
- Mention other files or behaviour only when they changed, or when they asked.
- Full sentences. No arrow chains, invented labels or names from your own reasoning.

## Handoff note

- Full sentences, no arrows, private labels or shorthand from the session.
- Done, not done, evidence, blockers and the next step, in that order.
- Name every check not run. A handoff is read cold, so define anything a new agent would not know.
- Record each scope decision the next agent might otherwise reopen, in one line with its reason.
- Vary sentence length. A run of 6-word sentences reads as a log; join facts that belong together.
